## 现象

用云浏览器（Browserbase 一类）自动化登录某内容平台，结果**还没到输入账号的步骤**，登录页就整个加载不出来，页面显示：

```
安全限制
IP at risk. Switch to a secure network and retry.
```

错误码 300012。第一反应：肯定是出口 IP 是数据中心 IP，被风控标记了。

## 排查第一步：查 IP 归属

用 IP 检测站点查当前浏览器出口 IP，结果出乎意料：

| 项目 | 值 |
|---|---|
| 归属 | 国内某省住宅宽带 |
| 运营商 | 联通（AS4837） |
| mobile / proxy / hosting | 全部 `false` |

也就是说出口 IP 是**国内正常住宅宽带**，不是机房、不是代理、不是 VPN。按照"IP 被拉黑"的假设，这说不通。

## 排查第二步：重新审视假设

IP 是住宅的，为什么还是被判风险？可能的原因收敛到两个：

1. **该 IP 在平台反作弊库里有历史记录**。比如这个 IP 段被大量注册过、或者之前被爬虫用过，进了风控黑名单。住宅 IP 也是会"脏"的——运营商的 NAT 出口是动态的，同一段 IP 可能被无数人用过，其中就包括机器行为。
2. **浏览器指纹暴露了自动化特征**。云浏览器有非常明显的自动化痕迹：WebDriver/CDP 控制标记、异常的 UA、缺插件、canvas 指纹怪异、行为轨迹过于规律。平台的反作弊引擎不只看 IP，还综合设备指纹、行为模型。**即便出口是干净的住宅 IP，自动化指纹照样被一眼识别。**

从现象判断，第 2 条嫌疑最大：拦截发生在登录页加载阶段，连账号都没输入，说明风控在**访问阶段**就已经基于指纹做出了决策。

## 排查 checklist（下次遇到"IP at risk"这么查）

1. **先查 IP 归属和类型**：`hosting/proxy/mobile` 三个标志位是否为 false。是机房 IP → 换住宅代理再试；是住宅 IP → 继续往下查。
2. **确认拦截发生在哪个阶段**：是页面加载就被拒（指纹/网络层风控），还是提交登录后才被拒（账号/行为风控）。阶段不同，根因完全不同。
3. **换真人浏览器对照实验**：在本地正常浏览器（非自动化）打开同一页面。能打开 → 基本坐实是自动化指纹问题；也打不开 → IP 或网络环境问题。
4. **重试排除偶发**：风控有时是概率性拦截，重试一两次排除误伤。
5. **检查自动化工具的特征**：webdriver 标记、`navigator.webdriver` 是否为 true、CDP 连接痕迹、UA 是否带自动化标识。

## 结论与教训

- **"风险 IP"不等于"机房 IP"**。住宅 IP 同样可能被风控，要么是 IP 段历史不干净，要么是浏览器指纹暴露了自动化。
- **云浏览器（Browserbase 等）的指纹是硬伤**。它是云上的 Chromium，自动化特征明显，反作弊引擎（尤其国内平台的）识别率很高，住宅 IP 也救不回来。
- **给敏感平台做自动化，先做"可控性评估"**：平台的登录页是否对自动化环境有强风控、是否需要住宅代理、是否需要指纹伪装（stealth 插件/反检测浏览器），这些应该在写脚本之前就确认，而不是等被拦了再排查。
- 如果是自己的账号被误伤，最稳妥的路径是**在真人设备上手动完成一次登录**，让账号和设备建立可信关系，后续自动化再基于已登录的会话进行。
