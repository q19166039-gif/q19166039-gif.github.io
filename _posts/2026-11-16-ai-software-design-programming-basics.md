## 第一课：程序到底是怎么工作的？

### 1. 五个关键词

**输入 → 判断 → 执行 → 循环 → 状态**，是理解很多自动化程序的入门框架。

- **输入（Input）**：接收行情、用户操作、文件内容或传感器数据。
- **判断（Condition）**：通过 `if` 等条件判断下一步该做什么。
- **执行（Action）**：发出操作、写入数据、生成报告或提交订单。
- **循环（Loop）**：按需重复处理新数据；循环必须有停止或退出机制。
- **状态（State）**：记录程序目前处于哪个阶段，如空闲、执行中、等待中。

### 2. 用量化交易举例

```text
接收最新行情
    ↓
检查行情是否完整、是否为已收盘K线
    ↓
计算指标、生成候选信号
    ↓
风控检查（仓位、杠杆、风险收益比等）
    ↓
允许执行？ ── 否 → 记录原因并等待下一轮
    │
    是
    ↓
提交订单 → 确认交易所回报 → 更新状态
    ↓
继续监控
```

**复习重点**：程序不是“想到哪写到哪”的指令堆砌，而是有明确输入、规则、动作和边界的流程。

### 3. 简短 Python 示例

```python
balance = 1000
price = 100

if balance >= price:
    print("余额充足，可以进入下一步检查")
else:
    print("余额不足")
```

这里仅演示条件判断；真实交易还需要独立风控、订单确认与异常处理。

## 第二课：状态机——让程序知道自己现在在干什么

### 1. 状态机的四个组成

| 英文 | 中文 | 含义 |
| --- | --- | --- |
| State | 状态 | 当前处于什么阶段 |
| Event | 事件 | 发生了什么事情 |
| Guard | 守卫条件 | 是否允许状态切换 |
| Action | 动作 | 切换时需要执行什么 |

例如，自动化程序可能有 `IDLE`（空闲）、`SEARCHING`（寻找目标）、`ATTACKING`（执行动作）、`WAITING`（等待）和 `STOPPED`（停止）等状态。

### 2. 交易系统状态示例

```text
NORMAL（空闲）
   │ 收到合格交易计划，且风控通过
   ▼
OPENING（开仓中）
   │ 交易所确认成交
   ▼
HOLDING（持仓中）
   │ 满足平仓条件
   ▼
CLOSING（平仓中）
   │ 确认仓位已经关闭
   ▼
NORMAL
```

若开仓失败、超时或网络中断，不能简单假定“没有成交”。应先核对交易所真实订单与仓位，再决定重试、恢复或人工介入。

### 3. 为什么状态机重要

- 防止重复提交订单。
- 避免尚未开仓成功就执行平仓逻辑。
- 限制非法状态转换。
- 使异常恢复过程可追踪。

**常见误区**：把所有问题都用增加一个 `if` 来解决。单个条件判断可以检查局部规则，但无法自动保证整个系统的状态一致性。

**设计原则**：程序记录的状态必须与外部真实世界（例如交易所实际持仓）定期核对。

## 第三课：函数、模块与接口——复杂程序如何分工

### 1. 三者的区别

**函数（Function）**：完成一件相对明确的事，可以接收参数并返回结果。

```python
def calculate_freight(weight, price_per_kg):
    return weight * price_per_kg

fee = calculate_freight(1200, 0.8)
print(fee)  # 960.0
```

**模块（Module）**：把相关函数、类与逻辑组织在一起。例如物流系统可以拆成：

```text
logistics/
├── main.py         # 总入口
├── order.py        # 运单管理
├── vehicle.py      # 车辆管理
├── dispatch.py     # 配载与调度
├── freight.py      # 运费计算
└── database.py     # 数据访问
```

**接口（Interface）**：不同模块交换信息时遵守的约定，包括输入字段、输出字段、错误格式等。

例如识别模块向操作模块返回：

```json
{
  "found": true,
  "x": 520,
  "y": 310,
  "target": "monster"
}
```

只要接口约定稳定，识别模块内部从传统图像匹配换成 AI 视觉识别，其他模块通常不必跟着大改。

### 2. 高内聚、低耦合

- **高内聚**：一个模块尽量专注于同一类职责。
- **低耦合**：模块之间减少不必要的相互依赖。

物流系统中，运费计算模块应专注运费规则，不宜直接承担车辆调度、数据库备份和用户登录等无关任务。

### 3. 指挥 AI 修改项目的检查清单

1. 先明确需求属于哪个模块。
2. 先分析调用关系与现有接口。
3. 尽量减少无关文件改动。
4. 如需改接口，同步检查所有调用方。
5. 补充测试，验证旧功能没有被破坏。
6. 交付修改清单、接口说明和测试结果。

## 第四课：数据结构——怎样组织数据

数据结构是存放和访问数据的方式。不同任务适合不同结构。

| 结构 | 英文 | 特点 | 典型场景 |
| --- | --- | --- | --- |
| 列表 | List | 有顺序、可遍历 | 车辆清单、K线序列 |
| 字典 | Dictionary | 键和值对应 | 按运单号查询运单 |
| 集合 | Set | 元素不重复 | 统计不同目的地、去重ID |
| 队列 | Queue | 先进先出 FIFO | 待处理任务 |
| 栈 | Stack | 后进先出 LIFO | 撤销操作、函数调用 |
| 树 | Tree | 父子层级关系 | 文件目录、组织架构 |

### 1. 列表：保存一组有顺序的数据

```python
vehicles = ["鲁A001", "鲁A002", "鲁A003"]
print(vehicles[0])  # 鲁A001
```

### 2. 字典：用字段名称定位信息

```python
order = {
    "运单号": "YD1001",
    "发货地": "淄博",
    "目的地": "许昌",
    "重量": 1200,
    "运费": 800
}
print(order["目的地"])
```

### 3. 集合：去掉重复数据

```python
cities = ["许昌", "漯河", "许昌", "驻马店"]
unique_cities = set(cities)
print(unique_cities)  # 集合不保证展示顺序
```

### 4. 队列和栈

```text
队列：先到先处理
A → B → C → 处理端

栈：最后放入的先取出
先放A，再放B，再放C → 先取C
```

### 5. 树：表达层级

```text
物流公司
├── 运输业务
│   ├── 许昌线路
│   └── 漯河线路
└── 车辆管理
    ├── 车辆A
    └── 车辆B
```

**实用判断**：需要顺序就考虑列表；需要按唯一键快速定位就考虑字典；需要去重就考虑集合；需要按到达顺序处理就考虑队列；需要层级关系就考虑树。

## 第五课：算法与复杂度——怎样判断代码效率

### 1. 算法是什么

算法是一套解决问题的明确步骤。比如查找某张运单，可以逐条检查，也可以在有序数据上采用二分查找。

### 2. 时间复杂度：数据增长时，工作量如何增长

| 复杂度 | 直观含义 | 典型示例 |
| --- | --- | --- |
| O(1) | 工作量基本不随数据量变化 | 字典按键查找的平均情况 |
| O(log n) | 每次缩小搜索范围 | 有序数据的二分查找 |
| O(n) | 数据越多，工作量线性增加 | 顺序遍历列表 |
| O(n log n) | 常见高效排序的增长级别 | 归并排序 |
| O(n²) | 数据翻倍，工作量可能约增四倍 | 两层嵌套逐一比较 |

> 复杂度描述增长趋势，不等于精确运行秒数；实际性能还受硬件、数据分布、网络、磁盘和实现细节影响。

### 3. 双重循环为什么可能慢

假设有 10000 张运单和 10000 个客户：

```python
for order in orders:
    for customer in customers:
        if order["客户"] == customer["名称"]:
            print("找到对应客户")
```

最坏情况下比较次数可达到约 `10000 × 10000 = 100000000` 次。

如果客户名称可作为唯一查询键，可以先建立字典：

```python
customer_map = {c["名称"]: c for c in customers}

for order in orders:
    customer = customer_map.get(order["客户"])
    if customer is not None:
        print("找到对应客户")
```

这样通常可以大幅减少重复查找。**注意**：如果客户名称不唯一，不能直接用名称作唯一键，否则会覆盖同名客户；应改用客户ID，或让一个键对应多个客户。

### 4. 空间复杂度：用多少额外内存

建立字典索引会多占用一些内存，但往往换来更快的查询。软件设计经常要在时间、空间、准确性和维护成本之间权衡。

### 5. 量化系统中的效率思路

- 尽量避免重复拉取同一批行情。
- 对可以增量更新的指标，评估是否需要每次全量重算。
- 对已处理事件使用集合或唯一ID去重。
- 按币种、订单ID、仓位ID建立可靠索引。
- 性能优化不能破坏已收盘K线确认、仓位核对与风控规则。


## 最后：给 AI 编程助手的通用要求

> 请先分析需求和现有项目结构，再设计实现方案。明确程序输入输出、主要状态、模块职责、接口契约和数据结构；说明关键算法的时间/空间复杂度，避免不必要的嵌套循环和重复计算。修改时尽量保持低耦合，特别注意异常恢复、外部状态核对与风险控制。完成后提交测试结果、修改清单及已知限制。不要仅以“代码能运行”作为验收标准。

## 自测：能回答这些问题，就算掌握了主线

1. 输入、判断、执行、循环、状态分别解决什么问题？
2. 为什么交易系统不能只靠几个 `if` 判断来维护订单状态？
3. 函数、模块和接口有什么区别？
4. 运单列表、运单详情、去重目的地、待处理任务分别适合什么数据结构？
5. 为什么双重循环在大数据量下可能很慢？
6. 什么情况下可以用字典索引代替反复遍历？
7. 你会要求 AI 提供哪些证据来证明代码修改可靠？

**一句话总结：** 你不需要先成为手写所有代码的程序员，但需要成为能看懂系统结构、识别风险、提出明确要求并验证结果的软件设计者。
