## 第一课：程序到底是怎么工作的？

一个自动化程序可以从五个关键词理解：**输入、判断、执行、循环、状态**。

- **输入**：读取行情、运单、文件或用户指令。
- **判断**：根据条件选择下一步动作。
- **执行**：更新记录、生成结果或提交操作。
- **循环**：持续处理新的任务，并有合理的退出机制。
- **状态**：记录当前处于空闲、执行、等待还是完成阶段。

例如量化交易的简化流程：

```text
读取行情 → 计算指标 → 判断信号 → 风控检查
                              ↓
                         执行或观望
                              ↓
                         更新持仓状态
                              ↓
                         等待下一轮
```

**注意**：真实交易系统不能只靠一条 `if` 判断下单。还要考虑订单失败、重复执行、断线恢复和交易所实际状态。

## 第二课：状态机（Finite State Machine）

状态机解决的问题是：**系统当前处于什么状态，发生什么事件后，允许转移到哪里？**

四个核心概念：

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| State | 当前状态 | NORMAL、OPENING、HOLDING |
| Event | 触发事件 | 收到开仓信号 |
| Guard | 转移条件 | 风控通过且无冲突订单 |
| Action | 转移时执行的动作 | 提交订单、记录日志 |

交易系统的简化状态路径：

```text
NORMAL → OPENING → HOLDING → CLOSING → NORMAL
             ↓          ↓
         异常处理 ← 交易所状态核对
```

状态机的重要价值是**阻止非法转移**。例如已经有未完成的开仓订单时，不能仅因为再次收到信号就重复下单。

实践提醒：**真实持仓状态与业务流程状态不一定是同一件事**。本地记录必须与交易所的实际订单、仓位核对；不能简单通过“修改合法转移表”掩盖状态不同步问题。

## 第三课：函数、模块与接口

把软件想象成一家物流公司：调度负责配车、财务负责运费、客服负责运单查询。软件也需要分工。

### 函数（Function）

函数把可重复的功能封装起来，通常接收参数并返回结果：

```python
def calculate_freight(weight, unit_price):
    return weight * unit_price

fee = calculate_freight(1200, 0.5)
print(fee)  # 600.0
```

### 模块（Module）

模块组织一组相关职责，例如：

```text
logistics/
├── main.py
├── orders.py       # 运单管理
├── dispatch.py     # 调度
├── vehicles.py     # 车辆
├── freight.py      # 运费计算
└── database.py     # 数据访问
```

### 接口（Interface）

接口是模块之间沟通的约定，包括输入、输出和错误处理。例如识别模块输出：

```json
{"found": true, "x": 320, "y": 180, "target": "monster"}
```

操作模块只需依赖这份数据约定，而不必知道识别模块内部使用传统图像匹配还是 AI 视觉模型。

两个重要原则：

- **高内聚**：一个模块内部的功能尽量围绕同一职责。
- **低耦合**：模块之间减少不必要的依赖。

给 AI 改项目时，应先让它列出模块职责、依赖关系、接口变化和测试范围，而不是直接修改大量无关文件。

## 第四课：数据结构

数据结构决定了程序怎样存放、访问和处理数据。

| 数据结构 | 特点 | 业务案例 |
| --- | --- | --- |
| List 列表 | 有顺序，可逐项访问 | K线序列、运单清单 |
| Dictionary 字典 | 键值对应，方便按键查询 | 运单详情、账户信息 |
| Set 集合 | 元素不重复 | 去重客户、已处理事件 |
| Queue 队列 | 先进先出（FIFO） | 待处理任务 |
| Stack 栈 | 后进先出（LIFO） | 撤销操作、函数调用 |
| Tree 树 | 表达层级关系 | 文件目录、业务分类 |

例如，一张运单可以用字典表达：

```python
order = {
    "运单号": "YD1001",
    "发货地": "淄博",
    "目的地": "许昌",
    "重量": 1200,
    "运费": 800,
}
print(order["目的地"])  # 许昌
```

而多张运单可以放在列表里：

```python
orders = [order]
```

如果要统计不同目的地，可以使用集合：

```python
cities = ["许昌", "漯河", "许昌", "驻马店"]
unique_cities = set(cities)
```

**核心认识**：不是所有数据都应该塞进列表。频繁按编号查找的场景，通常值得考虑字典或数据库索引。

## 第五课：算法与复杂度

算法是解决问题的一套明确步骤。时间复杂度描述的是**随着数据规模增加，工作量如何增长**，不是程序运行的精确秒数。

| 复杂度 | 直觉 | 典型例子 |
| --- | --- | --- |
| O(1) | 规模扩大，操作量基本不变 | 字典按键查找的平均情况 |
| O(log n) | 每次排除大量候选 | 有序数据的二分查找 |
| O(n) | 遍历全部数据 | 顺序扫描运单 |
| O(n log n) | 高效排序常见量级 | 归并排序 |
| O(n²) | 数据量翻倍，工作量约四倍 | 两层嵌套比较 |

### 例子：一万张运单匹配一万个客户

低效写法：

```python
for order in orders:
    for customer in customers:
        if order["客户"] == customer["名称"]:
            print("找到客户")
```

最坏情况下约进行 `10000 × 10000 = 100000000` 次比较。

更合适的思路是先建立字典索引：

```python
customer_map = {
    customer["名称"]: customer
    for customer in customers
}

for order in orders:
    customer = customer_map.get(order["客户"])
```

构建索引需要额外内存，但通常能减少大量重复查找。注意：这个示例假设客户名称唯一；实际业务更应使用稳定的客户 ID。

**空间复杂度**则关注算法需要的额外内存。设计软件经常需要在运行速度、内存占用、正确性和可维护性之间权衡。

### 在量化系统中如何应用

- 缓存已获取的行情，避免重复网络请求。
- 保存最近的闭合 K 线，避免无意义地重新加载全部历史数据。
- 对支持增量更新的指标考虑增量计算，但必须验证结果与完整计算一致。
- 用稳定的订单 ID、仓位 ID 关联记录。
- **性能优化永远不能绕过风控、状态核对与订单幂等性。**

## 五课知识如何串起来？

```text
程序逻辑：系统要做什么？
   ↓
状态机：当前允许做什么？
   ↓
函数 / 模块 / 接口：由谁负责，如何协作？
   ↓
数据结构：数据放在哪里，怎样访问？
   ↓
算法：怎样更有效率地处理？
   ↓
测试与验收：结果是否正确、稳定、安全？
```

## 给 AI 编程助手的通用要求

> 请先理解需求并绘制处理流程，明确模块职责、状态转换和接口契约；选择合适的数据结构，分析关键操作的时间与空间复杂度；优先小范围修改，不破坏既有功能；列出测试用例、边界条件、异常处理及验证结果。涉及交易、资金或真实业务数据时，正确性与安全性优先于性能。
